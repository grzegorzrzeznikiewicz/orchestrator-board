## Releases and updates

Only the fork repository may supply Orchestrator Board updates. An original-product release is a different application, even when its version is newer. Build configuration, bundled `app-update.yml`, runtime checks, feature releases, version-floor links, command-line bootstrap and repair must agree on the fork identity. A missing, malformed or foreign source must produce an error before networking or installation; it must not silently become “up to date”.

The current approved distribution is an unsigned DMG for personal use and manual installation/replacement, suitable for a separately authorized GitHub draft/prerelease upload without latest designation or updater feed files. No upload or publication is performed here. Apple signing/notarization and signed automatic updates are future work outside current OB-10 acceptance. Existing updater security remains in place.

Stable is the default channel. Existing nightly/feature selection remains within the same fork. Missing channel metadata must not select another repository or install a different channel. A valid feed with no newer version is different from an unavailable feed. Payload integrity and native signature/readiness checks remain mandatory. Cached or historical upstream update metadata is not evidence that a fork update is valid.

The build produces DMG and ZIP. DMG serves the current manual installation/replacement route. Future automatic macOS updates require ZIP update artifacts and `latest-mac.yml`. Full downloads remain enabled and macOS differential updates remain disabled. Release filenames and aliases must be verified against generated artifacts before documenting direct download URLs; this guide links the repository’s release list instead of guessing asset names.

## Data and coexistence

The existing daemon data location, `AO_DATA_DIR`, project paths, and Electron state under `~/.ao` remain authoritative. This task does not authorize moving or deleting existing data or rewriting the original application’s installation. Distinct bundle/executable/repair identity prevents accidentally selecting `Agent Orchestrator.app` as this fork’s target.

The daemon database, projects and durable settings remain in the existing data directory. Encryption-backed desktop state is separated because Electron derives its macOS/Linux encryption identity from the application name. The fork uses `~/.ao/orchestrator-board/electron` by default; an explicit `AO_DATA_DIR` uses `<resolved-data-dir>/orchestrator-board/electron`. The default developer profile is `~/.ao/dev/orchestrator-board/electron`; an explicit `AO_DEV_ELECTRON_DIR` remains an advanced override. The original `~/.ao/electron` and `~/.ao/dev/electron` are not opened, copied, moved or deleted by the new defaults.

Auth persistence uses `orchestrator-board-cloud-auth.bin` and the fork-specific legacy filename inside the existing data directory. Reads, decryption failure, unavailable protected storage and logout never touch original `cloud-auth.bin` or `cloud-session.json`. Browser cookies, sign-ins and UI-local preferences start separately; they are not silently migrated. Existing daemon projects/settings remain available. A fork update must preserve this same fork namespace across versions. A new updater cache/staging record does not authorize using a previously staged upstream payload.

The coexistence regression covers original-file byte preservation through read/write/logout and failed decoding, and profile path selection. This unit evidence does not prove native Keychain behavior; the final report must identify actual package/restart paths exercised.

A packaged fork can restore a deliberately selected launch configuration from `~/.ao/orchestrator-board/desktop-launch.json`. Version 1 requires `version: 1`, an absolute `dataDir`, an absolute `runFile`, and an integer `port` from 1 to 65535. Both paths must remain inside `~/.ao`, including after resolving symlinks. This makes an ordinary Finder/Dock launch use the same daemon data and fork Chromium profile as the selected installation. The app only reads this optional file: it never saves test-launch overrides automatically or moves existing data. An absent file retains the existing defaults; a present invalid selection stops startup with an error before opening a default database or profile.

An explicit nonblank `AO_DATA_DIR` bypasses the saved selection completely. Explicit `AO_RUN_FILE` and `AO_PORT` remain authoritative when loading a saved selection. Development launches ignore it. Keep machine-specific selections out of source and release artifacts, and verify a full quit followed by an ordinary Finder/Dock launch when accepting an installation that uses one.

An ordinary window opening restores the Kanban board of the last selected registered local project after the daemon's workspace list is ready. The choice comes from the existing profile-local project-open history, including a project selected through its chat; background session activity does not select a different project. Explicit project, session, settings, notification and remote routes take precedence. This restoration happens once per renderer start: choosing Home afterward keeps Home open. Missing projects, cloud/remote projects, Scratchpad, invalid history and unavailable local storage do not cause an automatic redirect or launch an agent.

The original hosted authentication return page emits `ao-app://`. The fork registers its own scheme and uses the existing loopback callback flow by default. An explicitly configured hosted return must emit the matching fork scheme. This source change does not deploy or reconfigure the original vendor’s cloud service. Live cloud sign-in/billing compatibility must not be claimed from parser tests alone.

## Accepting a suggested next message

A next-message suggestion stays a preview until the user chooses **Use suggestion** or presses **Tab** in the empty composer. Either action inserts an ordinary editable draft, focuses the composer and saves the draft without sending it. The send arrow sends only the accepted or independently typed draft. Escape dismisses the preview; typing an independent message keeps that message. Existing drafts and unavailable message-entry states do not expose the suggestion action. Accepted text supports undo and survives reopening the chat.
